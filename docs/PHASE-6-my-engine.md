# Phase 6 — Your own chess engine

Goal: a chess engine written from scratch in Java that plugs into the same
analysis pipeline as Stockfish, so you can analyse a game with either and compare.

## Where it fits

```
AnalysisRunner ──► Engine (interface) ──┬─► StockfishEngine   (talks to the stockfish program)
                                        └─► MyEngine          (pure Java, this phase)
                         ▲
                 EngineFactory.open("stockfish" | "my-engine")
```

Nothing in `AnalysisRunner`, `MoveAnalyzer` or the database changed. They only
know the `Engine` interface. That's the payoff of "program to an interface"
from Phase 5. The only new wiring is an `engine` parameter on the API and an
engine picker in the UI.

## Files

| File | Why |
|---|---|
| `engine/myengine/Evaluator` | Static evaluation: material + piece-square tables. |
| `engine/myengine/MyEngine` | The search: negamax, alpha-beta, quiescence, move ordering, iterative deepening, time limit. |
| `engine/EngineFactory` | Now builds either engine by name, and knows each one's maximum depth. |
| `application.yml` → `my-engine` | `max-depth: 5`, `time-limit-ms: 1500`. |
| `AnalysisService` / `AnalysisController` | `?engine=stockfish` or `?engine=my-engine` on POST and GET. |
| `AnalysisRepository` | `findFirstByGameIdAndEngineOrderByCreatedAtDesc`: each engine keeps its own latest analysis. |
| `frontend/src/pages/GamePage.tsx` | Engine tabs: switch to see each engine's verdicts on the same game. |

## How the engine thinks

### 1. Evaluation: "how good is this position, without looking ahead?"

```
score = material + where the pieces stand
```

- **Material:** P=100, N=320, B=330, R=500, Q=900 (centipawns).
- **Piece-square tables:** one 64-number table per piece type with a bonus for good squares.
  Knights in the centre +20, knights in a corner −50, pawns about to promote +50,
  and the king tucked behind its pawns +30 (in the endgame a different table
  pulls the king to the centre).

The score is from the **side to move**'s view. That's what negamax needs.

### 2. Search: negamax

```
score(position) = max over my moves of ( −score(position after the move) )
```

A position that is +3 for me is −3 for my opponent, so one function handles both sides.

### 3. Alpha-beta pruning

While searching we track **alpha** (what I can already guarantee) and **beta**
(the most my opponent will allow). If a move reaches ≥ beta, the opponent would
never let us get here, so we skip the remaining moves (**cut-off**). It gives the
same answer as full search, but looks at far fewer positions.

### 4. Move ordering (MVV-LVA)

Cut-offs come sooner if good moves are tried first: captures first, with the
**M**ost **V**aluable **V**ictim and **L**east **V**aluable **A**ttacker first
(PxQ before QxP). At the root, the best move from the previous depth goes first.

### 5. Quiescence search

If we stop at exactly depth 4, the last move might be "QxP", and we'd call it
+1 without seeing that the queen gets taken back. So at depth 0 we keep
searching **captures only** until nothing is hanging. The test
`doesNotGrabAPoisonedPawn` checks exactly this.

### 6. Iterative deepening + time limit

Search depth 1, then 2, 3, … until `max-depth` or the time limit is reached.
If time runs out in the middle of a depth, we use the last **finished** depth.
Mate is scored as `MATE − plies`, so the engine prefers the quickest mate.

## How strong is it? (measured)

Speed is about **400,000 positions per second**. Depth 5 takes 0.3–1.2 s per
position, and depth 6 takes 2–9 s.

On a real game (Hikaru vs ilovemypledgemaster, 70 moves):

| | Stockfish (depth 14) | My engine (depth 5) |
|---|---|---|
| Time for the whole game | ~25 s | ~52 s |
| Accuracy White / Black | 92.7% / 90.3% | 89.7% / 87.1% |
| Same best move as Stockfish | — | 25 of 70 |
| Same verdict as Stockfish | — | 45 of 70 |

It finds short tactics (mate in 1–2, hanging pieces) reliably, but misses
long-term strategy. Its opening moves (Nc3 everywhere) show that piece-square
tables alone don't "understand" openings.

**Why is Stockfish so much faster and stronger?** It uses *bitboards* (the board
as 64-bit numbers, with moves generated by bit tricks), makes moves in place and
undoes them instead of copying the board, keeps a *transposition table* (memory
of positions already searched), uses many pruning tricks, and has a neural-network
evaluation. Each of those is a possible next step for you.

## Tests (`MyEngineTest`)

Each position's answer was checked with Stockfish first:
- mate in 1, mate in 2, winning a hanging queen (for white and for black)
- not falling for a poisoned pawn (the quiescence search works)
- checkmate and stalemate positions
- the time limit is respected, and the start position evaluates to exactly 0 (the tables are symmetric)

## Try this (to make it stronger)

1. **Transposition table:** a `HashMap<String, Integer>` from FEN to score. It's easy to add and
   slow (FEN strings), but you'll see fewer nodes searched. Real engines use Zobrist hashing.
2. **Killer moves:** remember quiet moves that caused a cut-off at each ply and try them early.
3. **Check extension:** when the side to move is in check, search one ply deeper.
4. **Faster board:** replace `makeMove` (copy) with make/unmake on one board, and
   watch perft speed up. Keep `PerftTest` green while you do it!
5. Time a few `evaluate(fen, 5)` calls and print `nodes()` before and after each
   change, then re-analyse the same game to see whether it agrees with Stockfish more often.
